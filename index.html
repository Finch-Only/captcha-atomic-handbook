2｜人话流程：这一套东西到底怎么干活

给你一段能直接讲给同事听的白话：程序打开目标页面点「查询」，弹出了验证码。第一步，监控器盯住验证码弹窗，把它需要的图（底图、缺口图、提示词）截下来存到本地；第二步，调起识别引擎——它是一个独立的命令行小工具，吃进去图片路径和题型，吐出来一行 JSON 答案（比如"滑块往右拖 153 像素"），这一步完全离线、不联网、不碰页面；第三步，拿到答案后程序在页面上像人一样操作：先"看题"停 1~3 秒，拖动轨迹带抖动和回弹，点选之间有停顿，松手前精确落回目标位置；第四步，以服务端回执为准核对这道题到底过没过——页面没刷新不代表失败，可能回执只是在监听窗口外才回来，有台账可以补捞；第五步，过了就继续采集业务数据，没过就隔 60~75 秒换一道题再来（新一轮才允许换题），最多 4 轮，还不行就重载页面跳过这一页继续翻页，绝不卡死整轮。整个过程的每一个动作都写成事件日志，出问题能对着日志逐帧复盘。

三个最容易写错的坑（都是我们真实踩过的，详见第 11 节）：

① 验证码"通过"不等于业务请求已发出——验证码遮罩会拦住页面点击，通过后必须确认查询载荷真的回来了，没回来要主动补发；

② 页面没动静不等于提交失败——回执可能来得慢，要留台账补捞，别急着换题白白浪费请求次数；

③ 空结果（total=0）是合法结果——别把"没有行"当成"没加载成功"死等超时。

3｜三层架构：谁负责什么，换站点改哪层

层职责输入 → 输出换新站点时
第 1 层
识别原子
captcha-recognition		给一张题图 + 题型，算出候选答案。不做任何网页操作，不知道"验证码"来自哪个网站JSON（图片路径/题型/参考图）→ 一行 JSON（candidate / needs_human / error + 答案坐标或文本）零改动。新题型才需要加新算法
第 2 层
页面交互
captcha-auto.mjs		把"答案"变成"页面上的真实操作"，并核对服务端是否认账。绑定具体验证码组件（山西绑的是天爱 tianai 组件）页面弹码事件 → 题目截图、答案应用、回执判定按组件重写。经典图片码只要十几行（见云南）
第 3 层
调用协议
persistent-collector		决定调用节奏：几轮、隔多久、失败怎么办、怎么防限流。这一层是"像不像人"的关键业务翻页循环 → 每页的过码结果与事件日志参数级调整。逻辑直接复用
✅ 复用的正确姿势：第 1 层整包拿走；第 2 层按你站点的验证码组件重写（经典图片码只需"截图 → OCR → 填框 → 提交 → 校验"约 30 行）；第 3 层连逻辑带参数直接抄。

第 3 层翻到第 6 页 → 页面弹出天爱验证码大卡片，第 2 层监听器捕获题目（type=CONCAT）
截图取题 → 调识别引擎
底图存为 PNG，调用第 1 层 CLI（profile=shanxi-tac, type=concat），子进程 30 秒超时。引擎找出"竖直断缝 x=551、上下边界 y=175"，复原后色差下降 68.5 判定拼对了 → 返回 candidate（拖动 551−初始位 像素）
人化拖动
先"看题"停 1.2~2.8 秒 → 按下前停 150~400ms → 拖动轨迹分多步、带随机纵向抖动 → 接近目标时先冲过头 3 像素再回弹 → 松手前精确落回目标 → 松手
等服务端回执（以它为准）
监听 /captcha/check 响应：同一挑战 id + code 200 + success=true 才算"过"。页面还没刷新不算失败——回执台账留着，监听窗口外回来的"迟到回执"也能补捞（事件 captcha_auto_late_receipt）
等业务载荷，而不是急着重查
过码后站点会自动补发被拦住的查询。程序只等载荷回来（total=274），绝不主动重发查询——多发一次就是多一次风控暴露
记录事件、继续翻页
写一条 captcha_auto_solved（6.3s）到 captcha-events.jsonl，页间隔随机 5~9 秒后翻第 7 页

天爱组件（山西）的四种题型，识别引擎的算法一句话版：

题型题目长什么样需要输入算法（人话版）输出

WORD_IMAGE_CLICK图里散布汉字，按提示语顺序点选底图 + 提示词小图（保留透明通道）OCR 读出每个字的候选位置（普通 OCR + 旋转 OCR + 字形匹配多路投票），按提示语顺序排好坐标点选坐标列表
云南题型题目算法输出
generic数字+字母图片码（distort 文字）ddddocr 直接出文本文本（保留大小写、前导零）
⚠️ 引擎边界（哪些场景现在做不了）：无参考图的任意旋转、自由布局的点字、语序推断类、未知组件——这些需要单独适配算法；点字题遇到低对比图可能给不出候选（needs_human），靠换题兜底，不硬解。

6｜术语 → 人话翻译表

术语人话
candidate引擎给出了候选答案，但还不算数——要等服务端校验通过才算真的过
needs_human引擎说"这道题我给不出靠谱答案"，交人工或换题。不是报错，是正常输出之一（退出码仍是 0）
error输入或环境坏了（图片读不到、依赖缺），退出码 2，程序必须单独处理
天爱组件 / tianai / TAC山西政务站用的验证码前端组件（tianai-captcha），四种题型：滑块/旋转/拼接/点字
profile（generic / shanxi-tac）识别引擎的"档位"：generic 是通用图片码档；shanxi-tac 是按山西组件坐标和参考图特调的档
verifyCaptchaId过码后站点发的"通行证 id"，随后的业务请求带着它，服务端才知道你过了码
回执服务端对这道题的裁决（/captcha/check 返回 success=true）。唯一可信的"过了"凭证，页面没动不算失败、页面动了也不算成功
载荷业务查询真正返回的数据（列表 total、rows）。过码后它回来 = 业务请求真的发出去了
风控 / 限流站点发现"这不是人在操作"后的反制：弹"访问过于频繁"、429，甚至封。触发一次前功尽弃
爆破特征短时间窗内连续申请验证码、连续提交——机器才有的行为模式。人不会 3 秒内换 5 道题
迟到回执校验回执晚于程序的监听窗口才到达。程序留台账补捞，避免"实际过了却被记失败"
tuning.json识别引擎的成绩账本：每个题型累计尝试/通过数，评估识别率用
captcha-events.jsonl过码全过程的流水账（一行一个事件），排障就靠它逐帧复盘

7｜模拟人工调用协议：这套能力真正的护城河

先看对照实验（2026-11-06，同站点同 profile）

旧版：机器式调用新版：模拟人工
一页内行为识别失败就点刷新换题 → 多策略重解 → 同题重提 → 重发查询。一页打十几次 check/gen 接口只解当前这道题、只提交一次；没过就隔 60~75 秒换一道题开新一轮（最多 4 轮）
站点反应第 3 页即触发"访问过于频繁"，前功尽弃对照轮 332 页 + 后续所有例行轮：零限流
结论差异不在识别准确率，在一页内的请求次数。识别引擎 3 秒解出来也会因为调用方式像机器而被掐

五条铁律（写死在代码里，改任何站点都适用）

一页 = 一道题 = 一次提交
绝不主动点刷新换题、绝不多策略重解、绝不重发查询。人工就是这么干的
判定只认服务端回执
页面刷新了不算数、拖完了没反应也不算失败——回执台账补捞迟到回执，无真实回执绝不宣称通过
没过就按人的节奏等，再开新一轮
轮间隔 60~75 秒随机；新一轮才允许换一次题；单页上限 4 轮（CAPTCHA_AUTO_ROUNDS）
轮次用完 → 重载会话 → 跳页继续
连续失败说明这道题/这个会话有毒，重载页面重建会话，标记该页 skippedPages 后继续翻页，不中断整轮；跳过的页由上层检查并决定是否定点补采
一出现限流信号立刻停手
"频繁/稍后再试/429"一出现就不再提交（继续打只会加重风控），冷却 180 秒重试一次，仍限流才如实上报终止
💡 操作细节也在还原人：看题停 1.2~2.8s、按下前停 150~400ms、拖动轨迹带随机抖动并先冲过头 3px 再回弹、点字每点之间停 90~180ms、松手前精确落回目标。这些"不像机器"的细节加起来，就是风控眼里的"像人"。

8｜适配新站点 Checklist（照着做，8 步）

先判断验证码类型
经典图片文字码（数字/字母/算术）→ 用 generic 档，几乎零适配；滑块/旋转/拼接/点字组件 → 看是不是天爱组件（是 → 直接用 shanxi-tac 档；不是 → 第 5 步要写新映射）
部署识别原子（第 1 层）
拷贝 captcha-recognition 技能目录 → Python 3.12 建虚拟环境装依赖 → 跑一次 CLI 确认输出一行合法 JSON。点字题需要额外放两个模型文件（onnx + 字典，SHA256 见 contract.md）
离线验收，别直接上现网
收集 30~100 道带答案的样本题，测整题正确率和"错误放行率"（把错的当对的提交，比识别不出更危险）。成绩记进 tuning.json 作为基线
写第 2 层：取题与提交
监听验证码弹出 → 截下引擎需要的图（底图/参考图/提示词，透明通道要保留）→ 调 CLI → 把答案映射成页面操作。经典图码约 30 行；组件类要处理控件缩放（见第 11 节 CONCAT 教训）
写回执核对
找到服务端校验接口（F12 看验证码提交打到哪个 URL），监听响应：挑战 id + 成功标志。留最近 20 条台账补捞迟到回执
过码后等业务载荷，确认"通过≠请求已发出"
验证码遮罩可能拦住业务点击。过码后等查询载荷；载荷不来先查遮罩，确认被吞才补发（补发也算一次请求，能不发就不发）
接入第 3 层节奏 + 事件日志
一页一次提交、4 轮上限、轮间 60~75s、跳页不断轮、限流即停。每个动作写 jsonl 事件（字段见附录 B），上线第一天就能对着日志排障
灰度验收 → 上例行
先小窗口（单日/10 页）跑一轮人工盯梢，确认零限流、事件序列正常，再挂定时任务。例行轮每天看三个数：过码成功页数 / 换题轮次 / 限流次数

9｜参数调优表 + 耗时估算器

参数默认含义什么时候动它

CAPTCHA_ROUND_GAP_MS + _JITTER_MS60000+15000
（轮间 60~75s）		换题轮之间的等待别低于 60s（爆破特征红线）；赶时间也别压这个

CAPTCHA_HUMAN_MODE11=模拟人工；0=旧多轮重试只在离线诊断时用 0，现网永远 1

🔴 回退口诀：限流再现 → ① 批冷却回 60~90s → ② 页间隔回 8~15s → ③ 还不行说明站点升级了风控，回去看第 7 节是不是哪条铁律被"优化"掉了。

11｜踩坑复盘（4 个真实事故，比成功经验值钱）

事故 1｜CONCAT 永远 no_verdict：一个会等待的 DOM 查询拖垮了 12 秒回执窗口

现象：拼接题拖动明明成功了，程序却总记"无裁决"，再白等 90 秒换题——每道拼接题都浪费一次提交机会，还差点被当成"识别能力不行"。

真凶：取控件缩放比例的函数用了一个会自动等待元素出现的查询去找底图 <img>，但拼接题根本没有这个 img（底图是 DIV 的 CSS 背景）→ 静默等满 30 秒超时；而回执监听窗口只有 12 秒，在拖动开始前就过期了。拖动成功、回执也回来了，只是没人接。

修复：① 缩放读取改为一次性同步读 DOM，按 img → DIV 背景 → 整个组件三层候选依次取；② 回执加台账，超时后按挑战 id 补捞 1.5 秒内的迟到回执；③ 无真实回执绝不宣称通过（宁可信其未过）。

教训：验证码组件是前端 JS 动态渲染的，每个题型在 DOM 里的结构可能完全不同；任何"会等待"的查询放在时序敏感的路径上都是定时炸弹。

事故 2｜验证码"通过"≠ 业务请求已发出：遮罩吞了点击

现象：过码后页面迟迟不刷新，程序误判"会话失效"反复重来。

真凶：验证码遮罩层会拦截页面 pointer 事件，如果"查询"按钮的点击落在遮罩之下，请求根本没发出去，过码后站点也不会自动补发。

修复：过码后先等业务载荷（8 秒），确认被吞才主动补发一次（补发也要计入请求次数预算）；同时把"空结果（total=0 且 rows=[]）"改成合法载荷，不再误判（事故 3 的另一半）。

事故 3｜空结果被当成加载失败

现象：查询窗口内确实没有数据（节假日无批复），程序以"表格没出现行"判定加载失败，死等到超时。

修复：加载判定从"等行出现"改为"等载荷"——total=0 且 rows=[] 是合法结果，直接进入下一步。

事故 4｜机器式调用触发限流：3 页 vs 332 页的对照实验

现象：自动识别 3 页就弹"访问过于频繁"；但人工填码连跑 332 页零风控。

定位：逐条比对两者的请求序列，发现差异全在一页内的请求次数——旧版识别失败会换题、多策略重解、同题重提、重发查询，一页打十几次接口，是教科书级的爆破特征。

修复：整章重写为第 7 节的模拟人工协议。修复后所有例行轮零限流。这是整套能力里价值最大的一次重构——它证明了调用方式比识别算法更早成为瓶颈。

12｜边界与合规（先说清楚，免得用错方向）

① 只解公开页面上的公开数据验证码（政务公开列表、公示页）。登录态、付费墙、需个人身份的页面一律不适用。

② 不绕过、不破解加密、不打接口漏洞——我们做的是"把人过码的动作自动化并放慢到人的节奏"，本质是降低无意义的人力消耗，不是对抗风控。协议里所有"像人"的设计同时也在控制请求总量，对站点更友好。

③ needs_human 是能力的一部分，不是失败：识别不出的题交人工或换题，绝不硬解；被限流立即停手，绝不重试轰炸。

④ 数据仅用于已授权的内部数据需求登记流程，采集范围、频率、字段都有登记可查。

附录 B｜事件字典（captcha-events.jsonl）

事件含义健康状态应该长什么样
captcha_prompt弹出验证码（人工等待模式）—
captcha_auto_solved自动识别 + 提交 + 回执确认通过每页 1 条，数量≈页数
captcha_auto_attempt一次识别尝试（含 verdict：solved/needs_human/no_verdict…）绝大多数页 1 次
captcha_auto_round_failed本轮未过，进入轮间等待偶发
captcha_auto_round_gap换题轮间等待（60~75s）偶发
captcha_page_exhausted单页 4 轮用完罕见；连续出现要查识别率
session_reset重载页面重建会话（跳页前）罕见
captcha_auto_late_receipt迟到回执补捞成功（避免误判失败）偶发，属于修复机制在起作用
captcha_auto_throttled检测到限流必须为 0；非 0 立即停手并上报
captcha_auto_unavailable识别引擎不可用（CLI 缺失/环境坏）必须为 0
captcha_timeout人工等待超时（全自动模式下不应出现）必须为 0
💡 例行巡检三看：captcha_auto_solved 数 ≈ 页数（覆盖完整）、captcha_auto_throttled = 0（没被风控）、captcha_timeout = 0（没退化到人工等待）。checkpoint.json 里还有 partial 和 skippedPages——就算 status=completed，这两个字段非空就说明有页没覆盖。
